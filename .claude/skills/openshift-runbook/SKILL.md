# openshift-runbook

`T` はこのスキルの `scripts/runbook.sh`（プロジェクトに置いた場合は `.claude/skills/openshift-runbook/scripts/runbook.sh`）。`bash $T` を実行し、出力の `案内:` と `次:` に従う（手順は Git リポジトリのルートの `runbooks/<name>/` に置かれる）。ただし、「ユーザーに確認すること」にある操作は、`次:` があっても確認してから行う。

引数に応じて、下の番号付きの節を順に行う。

| 引数 | 流れ |
|---|---|
| なし | 1. 依頼の確認 → 回答に応じて下のいずれか |
| `<実現したいこと>` | 2. クラスタの確認 → 3. 手順の作成 → 5. 検証 |
| `plan <name>` | 2. クラスタの確認 → 4. 適用内容の表示 |
| `run <name>` | 2. クラスタの確認 → 5. 検証 |
| `cleanup <name>` | 2. クラスタの確認 → 6. クリーンアップ |
| `doc <name>` | 7. 手順書の再生成（クラスタに接続しない） |

## ユーザーに確認すること

AskUserQuestion で確認し、回答なしに進めない。既に得た承認を引き継ぐのは、同じ接続先・同じ手順の内容の場合だけ。ファイルを直したら、plan を示し直して確認する（修正案の了承と一緒に確認してよい）。

| 場面 | 確認すること |
|---|---|
| 1. 依頼の確認 | 何を実現したいか。クラスタに接続する前に聞く |
| 2. クラスタの確認の後 | 表示されたユーザー・API サーバー・バージョンで作業してよいか |
| 3. 手順の作成で成功条件を書いた後 | spec.md の `## 成功条件 (DoD)` でよいか。合意するまでステップのファイルを作らない |
| 5. 検証の前 | `plan` の内容（成功条件、パラメータ、適用するもの）を適用してよいか、パラメータの値がこのクラスタに合っているか（パラメータがある場合）、検証後にクリーンアップするかリソースを残すか（既定: クリーンアップ） |
| 6. クリーンアップの前 | `plan` が示す、削除・切り戻しするもの。検証のやり直しで、残ったリソースを消すときも同じ |
| 強制削除の前 | finalizer の除去など |

## 1. 依頼の確認（引数なし）
`bash $T list` の表をそのまま示し、何を実現したいかを聞く。既存の手順に対する plan（適用内容の確認）/ run（再検証）/ cleanup / doc も選べることを添える。推測で決めたり、例を選んで進めたりしない。

## 2. クラスタの確認（cluster）
`bash $T cluster` を実行する。
- NG: `案内:` を伝えて終える。sandbox の通信制限が疑われる場合は、承認を得て sandbox 外で再試行する。ユーザー側の設定が原因と断定しない。
- OK でも接続先が違う場合: 正しいクラスタへの `! oc login …` か `! oc config use-context …` を依頼して終える。切り替えたら最初からやり直す。

## 3. 手順の作成（new / lint）
1. **公式ドキュメント**: `cluster` が表示したバージョンのドキュメントを WebFetch で読み、該当する章の Procedure と Verification を確かめる（本文が出なければ `offset` で続きを読む）。記憶や別バージョンの知識だけで書かない。OpenShift のドキュメントに無いもの（Red Hat 以外の Operator など）は提供元の該当バージョンを読み、どちらも無ければユーザーに伝える。クラスタは読み取りなら調べてよい。
2. **成功条件 (DoD)**: `bash $T new <name>` でひな形を作り（手順名は英小文字・数字・ハイフン）、spec.md の `## 成功条件 (DoD)` にチェックリストを書いて合意を得る。
   ```
   - [ ] Route の URL に HTTPS でアクセスすると HTTP 200 が返る。（確認: 04-route）
   ```
   - 各項目は、完了したときにユーザーが観測できる状態にする。起動・リソース作成・目的の機能が使えることを区別し、検証を通すために緩めない。判断できない重要な点だけ聞く。
   - `（確認: NN-name）` は、その状態を確かめる check.sh のステップ。ステップの構成も、ここで決まる。
   - チェックは付けない。`run` で確認できた項目に、検証結果と runbook.md で [x] が付く。
3. **ファイル**: [references/writing-guide.md](references/writing-guide.md) に従って、spec.md の残りとステップを書く。各成功条件は、指定したステップの check.sh で確かめる。
4. **lint**: `bash $T lint <name>` を、`[NG]` と `[WARN]` が無くなるまで直す。成功条件を変えた場合は、もう一度合意を得る。

## 4. 適用内容の表示（plan）
`bash $T plan <name>` の出力（成功条件、パラメータ、適用するもの、既に存在するもの、前回から残っているもの）をそのまま示す。クラスタは変更しない。`[NG]` があれば、`案内:` と `次:` を伝える（既に存在するリソースがあると run は開始しない）。`plan` だけを指定された場合は、ここで終え、実行するなら `/openshift-runbook run <name>` を案内する。

## 5. 検証（run）
1. 「4. 適用内容の表示」を行い、「ユーザーに確認すること」の「5. 検証の前」を確認する。
   - パラメータの値が合わない、または足りない場合は、値を聞いて spec.md の `## パラメータ` と該当するファイルを直し、`bash $T lint <name>` を通してから、もう一度「4. 適用内容の表示」と確認を行う。直すと、それまでの検証結果は「検証後に変更」の扱いになる。
2. `bash $T run <name> --cleanup`（残す場合は `--keep`）を `run_in_background` で実行し、完了の通知を待つ（待ち時間の長いステップがあるため、Bash の timeout で中断させない）。runbook.md まで作られる。
   - `--keep` を選んだ場合は、rollback.sh が検証されないこと、後で cleanup で元に戻せることを伝える。
3. 終了コードが 0 以外の場合は、`次:` に従う。
   - 3（開始できない）: 何も変更していない。接続・lint・既存リソース・前回の残りのどれが原因かを伝える。
   - 130（中断）: リソースが残っている可能性がある。「6. クリーンアップ」を行う。
   - 1（手順の失敗）または 2（切り戻しかクリーンアップの問題）:
     1. `次:` のログと読み取りだけの調査（`oc get` / `describe` / `logs` / `events`）で原因を特定する。
     2. リソースが残っていれば、ファイルを直す前に「6. クリーンアップ」を行う（YAML は適用したときの内容で削除される）。ただし rollback.sh の不具合で切り戻せない場合は、rollback.sh だけを先に直してからクリーンアップする。
     3. 修正案を示し、了承を得てからファイルを直し、やり直す（最大 2 回）。
     4. 達成できない場合は、原因を添えて未達成と報告する。
4. 検証で分かった待ち時間や挙動は、該当するステップに `# 注記:` で追記する。
5. runbook.md を読み、成功条件と出力例の対応、コマンドの改行・引用符、注記、出力例の長さ、手動での切り戻し・削除の手順を確かめる。直すときは元のファイルを直し、実行内容を変えたら再検証、説明だけなら「7. 手順書の再生成」を行う。

## 6. クリーンアップ（cleanup）
「4. 適用内容の表示」で削除・切り戻しするものを示し、確認してから `bash $T cleanup <name>` を実行する。
- 検証したときと今の接続先（クラスタまたはプロジェクト）が違う場合、cleanup は何もせずに終える。`案内:` に従い、検証したクラスタとプロジェクトへの切り替え（`! oc config use-context …` / `! oc project …`）を依頼する。
- rollback.sh が「この手順で作成していないリソースがある」と止まった場合は、何が残っているかを伝え、どうするかをユーザーに聞く。
- 削除できなかった、または削除を確認できなかったリソースが表示されたら、それを報告する。

## 7. 手順書の再生成（doc）
`bash $T doc <name>` で runbook.md を作り直す。クラスタには接続しない。runbook.md は直接編集せず、元のファイル（spec.md、manifests/、scripts/）を直してから作り直す。

## 完了報告
各段階の結果と runbook.md のパスを報告する。`[WARN]`（未検証、FAIL、検証後に変更）が出たら伝える。リソースが残っている場合は、そのことと `/openshift-runbook cleanup <name>` を伝える。

## ルール
- `oc login`、コンテキストの切り替え、ツールのインストールは自分で実行せず、`! oc login …` のようにユーザーに依頼する（Bash で実行するコマンドには `!` を付けない）。トークンは表示しない。
- スクリプトが行う処理を、手でコマンドを打って代わりに実行しない。手順を変えるときはファイルを直す。
