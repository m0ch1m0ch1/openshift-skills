# openshift-runbook

`T` は `bash .claude/skills/openshift-runbook/scripts/runbook.sh` の略で、リポジトリのルートからこの形のまま実行する。出力の `案内:` と `次:` に従う（手順は Git リポジトリのルートの `output/openshift-runbook/<name>/` に置かれる）。ただし、「ユーザーに確認すること」にある操作は、`次:` があっても確認してから行う。

下の番号付きの節を順に行う。

## ユーザーに確認すること

AskUserQuestion で確認し、回答なしに進めない。既に得た承認を引き継ぐのは、同じ接続先・同じ手順の内容の場合だけ。ファイルを直したら、適用内容を示し直して確認する（修正案の了承と一緒に確認してよい）。ただし、検証後にクリーンアップするかリソースを残すかは、引き継がず、`run` を実行するたびに（やり直しでも）聞く。

| 場面 | 確認すること |
| --- | --- |
| 1. 依頼の確認 | 何を実現したいか（引数が無い場合）。クラスタに接続する前に聞く |
| 2. クラスタの確認の後 | 表示されたユーザー・API サーバー・バージョンで作業してよいか |
| 3. 手順の作成の最初（MCP が使えない場合） | 使えない MCP ごとに、導入せずに進めてよいか（「導入せずに進める」「導入する」から選んでもらう）。使えると何ができるかを添える（rhdocs: 公式ドキュメントを要約されずに読める。rhkcs: ナレッジベースで既知の問題を確かめられる） |
| 3. 手順の作成で成功条件を書いた後 | spec.md の `## 成功条件 (DoD)` でよいか。合意するまでステップのファイルを作らない |
| 4. 検証の前 | 適用内容（成功条件、パラメータ、適用するもの）を適用してよいか、パラメータの値がこのクラスタに合っているか（パラメータがある場合）、検証後にクリーンアップするかリソースを残すか（「クリーンアップする」「リソースを残す」から選んでもらう。どちらにも（推奨）を付けない。残す場合は、切り戻しまで検証してから再適用するので時間が約 2 倍かかることを添える。依頼の中で指定があっても、この時点で選んでもらう） |
| 検証のやり直しで、残ったリソースを消す前 | 削除・切り戻しするもの |
| 強制削除の前 | finalizer の除去など |

## 1. 依頼の確認

引数があれば、それを実現したいこととして 2 に進む。引数が無ければ、何を実現したいかを聞く。推測で決めたり、例を選んで進めたりしない。

## 2. クラスタの確認

`T cluster` を実行する。

- NG: `案内:` を伝えて終える。sandbox の通信制限が疑われる場合は、承認を得て sandbox 外で再試行する。ユーザー側の設定が原因と断定しない。
- OK でも接続先が違う場合: 正しいクラスタへの `! oc login …` か `! oc config use-context …` を依頼して終える。切り替えたら最初からやり直す。

## 3. 手順の作成

1. **MCP の確認**: Red Hat ドキュメントの MCP（rhdocs: `mcp__rhdocs__redhat_docs_search` と `mcp__rhdocs__redhat_docs_fetch`）と、Red Hat ナレッジベースの MCP（rhkcs: `mcp__rhkcs__search_kcs` と `mcp__rhkcs__get_kcs`）が使えるかを確かめる。ツールの一覧に無ければ ToolSearch で `rhdocs`・`rhkcs` を探す（Claude Code が無効・使えないと知らせていれば、探さずに使えないとする。`mcp__rhdocs__authenticate` しか無ければ、rhdocs は認証されていないので使えないとし、自分で認証を始めない）。使えないものがあれば、「ユーザーに確認すること」の「3. 手順の作成の最初」を確認する。
   - 導入する場合: rhdocs は、`/mcp` で `rhdocs` を選び、無効なら有効（Enable）にし、認証されていなければ Authenticate を選んで Red Hat アカウントでログインするよう依頼し、済んだと言われたら確かめ直す。rhkcs は、`/rhkcs-mcp-setup` で導入してから、このスキルを実行し直すよう伝えて終える。
   - 導入せずに進める場合: 使えないものは使わずに進める。
2. **公式ドキュメント**: `cluster` が表示したバージョンのドキュメントを読み、該当する章の Procedure と Verification を確かめる。記憶や別バージョンの知識だけで書かない。OpenShift のドキュメントに無いもの（Red Hat 以外の Operator など）は提供元の該当バージョンを読み、どちらも無ければユーザーに伝える。クラスタは読み取りなら調べてよい。
   - 1 で rhdocs が使えれば、Red Hat のドキュメントは、`redhat_docs_search` で章を探し、`redhat_docs_fetch` で章のページを読む。検索語は英語にし、`OpenShift Container Platform <x.y>` と機能名を入れる（クラスタ固有の値は入れない）。検索結果には別のバージョンも混じるので、URL のバージョンを確かめる。`fetch` の `query` に英語の節の名前を渡すと、章の中の節が 1 つ（`<x.y>` の単位で）返るが、違う節が返ることがあるので、目的の節が含まれるかを確かめる（無ければ `query` なしで章全体を読む）。検索結果の `abstract` は `<…>` が抜けるので、手順は `fetch` で読んだ本文から書く。
   - rhdocs が使えないときと、Red Hat 以外の提供元のドキュメントは、WebFetch で読む（本文が出なければ `offset` で続きを読む）。
3. **既知の問題**: 1 で rhkcs が使えれば、機能名とバージョンで探して読み、このバージョンの不具合・前提条件・時間がかかる理由があれば、成功条件・待つ時間・注記に反映する（書き方は writing-guide の「コメント」）。手順は公式ドキュメントに従い、記事の手順やコマンドはそのまま使わない（コマンドは空白が抜けている）。rhkcs が使えなければ飛ばす。
4. **成功条件 (DoD)**: `T new <name>` でひな形を作り（手順名は英小文字・数字・ハイフン。既にある名前は使えない）、spec.md の `## 成功条件 (DoD)` にチェックリストを書いて合意を得る。

   ```markdown
   - [ ] Route の URL に HTTPS でアクセスすると HTTP 200 が返る。（確認: 04-route）
   ```

   - 各項目は、完了したときにユーザーが観測できる状態にする。起動・リソース作成・目的の機能が使えることを区別し、検証を通すために緩めない。判断できない重要な点だけ聞く。
   - `（確認: NN-name）` は、その状態を確かめる check.sh のステップ。ステップの構成も、ここで決まる。
   - チェックは付けない。検証で確認できた項目に、検証結果と runbook.md で [x] が付く。
5. **ファイル**: [references/writing-guide.md](references/writing-guide.md) に従って、spec.md の残りとステップを書く。各成功条件は、指定したステップの check.sh で確かめる。
6. **lint**: `T lint <name>` を、`[NG]` と `[WARN]` が無くなるまで直す。成功条件を変えた場合は、もう一度合意を得る。

## 4. 検証

1. `T plan <name>` の出力（成功条件、パラメータ、適用するもの、既に存在するもの）をそのまま示し、「ユーザーに確認すること」の「4. 検証の前」を確認する。
   - `[NG]` があれば、`案内:` と `次:` を伝える（既に存在するリソースがあると検証は開始しない）。
   - パラメータの値が合わない、または足りない場合は、値を聞いて spec.md の `## パラメータ` と該当するファイルを直し、lint を通してから、もう一度 plan を示して確認する。
2. 1 の回答に従って `T run <name> --cleanup` か `T run <name> --keep` を `run_in_background` で実行し、完了の通知を待つ（待ち時間の長いステップがあるため、Bash の timeout で中断させない）。runbook.md まで作られる。
   - `--keep` は、`--cleanup` と同じく切り戻しとクリーンアップまで検証してから、もう一度適用してリソースを残す。ステップ・切り戻し・クリーンアップのどれかが OK でなければ再適用しない（切り戻しかクリーンアップに失敗した場合は、リソースが残っていることがあるので、`次:` に従う）。実行中にファイルが変わった場合も、検証していない内容を残さないように再適用しないので、変更した内容でやり直す。再適用が失敗した場合（終了コード 1）は、切り戻しで元の状態に戻っていない可能性があるので、`run/logs/reapply/` のログで原因を調べる。
3. 終了コードが 0 以外の場合は、`次:` に従う。
   - 3（開始できない）: 何も変更していない。接続・lint・既存リソースのどれが原因かを伝える。
   - 1（手順の失敗。`--keep` の再適用の失敗を含む）、2（切り戻しかクリーンアップの問題）、130（中断。`--keep` の再適用の途中で中断した場合も、手順書は未検証になる）:
     1. `次:` のログと読み取りだけの調査（`oc get` / `describe` / `logs` / `events`）で原因を特定する。3.1 で rhkcs が使えれば、エラーメッセージ（クラスタ名・ホスト名・IP アドレスを除いた部分）でナレッジベースも探し、既知の問題かを確かめる。
     2. リソースが残っていれば、ファイルを直す前に `T plan <name>` で削除・切り戻しするものを示し、確認してから `T cleanup <name>` を実行する（YAML は適用したときの内容で削除される）。ただし rollback.sh の不具合で切り戻せない場合は、rollback.sh だけを先に直してから cleanup する。
        - 接続先（クラスタまたはプロジェクト）が検証したときと違う場合、cleanup は何もせずに終える。`案内:` に従い、切り替え（`! oc config use-context …` / `! oc project …`）を依頼する。
        - rollback.sh が「この手順で作成していないリソースがある」と止まった場合（検証中も同じ。そのときは YAML も削除されない）は、何が残っているかを伝え、どうするかを聞く。
     3. 修正案を示し、了承を得てからファイルを直し、4.1 から（plan を示し、「4. 検証の前」を確認して）やり直す（最大 2 回）。
     4. 達成できない場合は、原因を添えて未達成と報告する。
4. 検証で分かった待ち時間や挙動は、該当するステップに `# 注記:` で追記し、`T doc <name>` で runbook.md を作り直す（コメントなので、検証結果は古くならない）。
5. runbook.md を読み、成功条件と出力例の対応、コマンドの改行・引用符、注記、出力例の長さ、アクセス情報（URL が検証で作られたものと合っているか）、切り戻しの手順を確かめる。runbook.md は直接編集せず、元のファイル（spec.md、manifests/、scripts/）を直す。実行内容を変えたら 4.1 から再検証し、説明だけなら `T doc <name>` で作り直す。`--keep` で残したリソースがあるときは、再検証の前にそれを削除してよいかを確認する（削除しない場合は、runbook.md が「検証後に変更」のままであることを伝える）。

## 完了報告

各段階の結果と runbook.md のパスを報告する。リソースを残し、spec.md に `## アクセス情報` があれば、その表も示す。`[WARN]`（未検証、FAIL、検証後に変更）が出たら伝える。リソースを残した場合や、削除できなかったリソースがある場合は、そのことと、元に戻す方法（`T cleanup <name>`）を伝える。

## ルール

- `oc login`、コンテキストの切り替え、ツールのインストールは自分で実行せず、`! oc login …` のようにユーザーに依頼する（Bash で実行するコマンドには `!` を付けない）。トークンは表示しない。
- スクリプトが行う処理を、手でコマンドを打って代わりに実行しない。手順を変えるときはファイルを直す。

## 手順書の実行

- 手順書は「次のコマンドを実行します → 出力例」の形式で示す。前提条件に、作成するリソースがまだ存在しないことを含める。
- 前提条件に、manifests/ と scripts/ (rollback.sh を含む) を手順書と同じディレクトリにあらかじめ配置し、そこでコマンドを実行することを明記する。YAML の手順ではファイルを新規作成せず、配置済みファイルの内容が掲載した YAML と一致することを確認する。
- 手順の先頭で、manifests/ のすべての YAML に対して `oc get -f <各YAML> --ignore-not-found -o name` を実行し、何も表示されないことを確認する。リソース名が表示された場合は中止する。no matches for kind / resource mapping not found（CRD がまだ登録されていない）は、そのリソースがまだ存在しないものとして続行する。それ以外のエラー（権限・通信など）で確認できない場合は中止する。
- 切り戻しは `bash scripts/rollback.sh` を実行する。「止めます」と表示された場合や失敗した場合は次へ進まない。正常終了後、YAML を適用時と逆の順序で削除する。rollback.sh の内容は実行コマンドの下に参考として載せ、ブロックごとには実行させない。

- 指紋は manifests/・scripts/ のコメント行と YAML の行末の説明コメントを除いた内容、および spec.md の成功条件・パラメータから計算する。コメントだけの変更では検証済みのまま、`doc` で手順書を作り直せる。実行内容を変更したら再検証する。

## 安全な実行と記録

- スキルのスクリプトが扱う手順はリポジトリ内に置く。読み込むパスの `..` とシンボリックリンク（内部向けも含む）は拒否する。適用記録には `run/applied/NN-name.yaml` だけを許可し、絶対パスは受け付けない。
- 記録の準備・保存に失敗したら、対応するクラスタ変更を始めない。スキルが実行する切り戻しスクリプトは、ファイルへの展開と構文検査に成功した場合だけ実行する。
- 相対パスの `RUNBOOK_DIR` は実行時のカレントディレクトリを基準に絶対パスへ変換してから、安全性を検査する。
- cleanup は YAML を逆順に削除し、存在しないことを確認できたものから適用記録を外す。途中で失敗・中断したら、残りを次の cleanup で再開する。適用一覧の更新用一時ファイルは、同じファイルシステム内で置き換えるため run/ に作る。
- その他の一時ファイル・kubeconfig は Git 管理対象外の `output/openshift-runbook/.runtime/` に置く。終了時に通常ファイルと空ディレクトリを順に削除する。
