# openshift-must-gather-analysis

ユーザーが示した 1 つの事象の原因を突き止める。クラスタ全体の点検はせず、事象から原因へさかのぼる道筋の上だけを調べる。

`mg.sh` は `bash .claude/skills/openshift-must-gather-analysis/scripts/mg.sh` の略で、リポジトリのルートからこの形のまま実行する。出力の `次:` と `案内:` に従う。調べ方・コマンド・報告書の書き方は [references/analysis-guide.md](references/analysis-guide.md)（以下「ガイド」）に従う。

番号の順に進める。ユーザーに聞くのは、各段に書いたことだけにする。

## 1. omc と MCP の確認
1. `mg.sh check` を実行する。`[NG]` なら「omc が無いので入れてほしい」と伝え、`案内:` の GitHub の URL を示して終える。
2. Red Hat ナレッジベースの MCP（`mcp__rhkcs__search_kcs` と `mcp__rhkcs__get_kcs`）が使えるかを確かめる。ツールの一覧に無ければ ToolSearch で `rhkcs` を探す（Claude Code が、rhkcs は無効・使えないと知らせていれば、探さずに使えないとする）。使えれば 7 で使う。使えなければ「`/rhkcs-mcp-setup` で導入すると、ログインが必要な記事も読める」と 1 行伝え、使わずに進める（聞かない）。

## 2. must-gather の準備
1. `mg.sh new` を実行し、表示された置き場所に must-gather を置くよう案内する。ユーザーがケースの番号などを示していれば `mg.sh new <case>`。引数に事象があれば控えておき、ここでは事象を聞かない。
2. 置いたと言われたら `mg.sh prepare <case>` を実行する。`[NG]` なら `案内:` を伝えて待つ。

## 3. 事象と確認事項
1. must-gather の取得日時（日本時間も）とクラスタのバージョンを示し、事象のうち、何が・いつから・どこで・エラーメッセージ・直前の変更の足りない点だけを聞く（引数が無ければ、すべて聞く）。
   - 事象の時刻が取得日時より後なら、この must-gather では確かめられないことを伝える。
   - 事象に OpenShift 本体以外の製品（CSI Driver、Operator など）が関わるなら、`mg.sh ns <case>` でその Namespace の Pod とログがあるかを確かめ、無ければ `案内:` のとおり追加の資料を依頼する。取れなければ「未確認事項」に回す。
2. `mg.sh plan <case>` で確認事項のファイル（`checklist.md`）を作り、ガイドの「確認事項と調査項目」に従って、「事象」「確認事項」「調査項目」を書く。
3. `mg.sh items <case>` の出力（確認事項と調査項目）を、そのままユーザーに示す。足りない確認事項があれば、足す。

## 4. 調査の起点の決定
`mg.sh overview <case>` を実行し、事象が現れている場所（ClusterOperator、Pod、ノードなど）を起点として示す。起点に合わせて調査項目を見直す（具体的なリソース名を入れる、項目を足す）。
- 事象と関係のない異常は示さない。関係があるか判断できない異常は 1 行で触れ、調べるかをユーザーに任せる。
- 「最近のアップデート」が事象の時刻と重なっていれば添える。
- 起点が overview に無い（設定や運用の問題）なら、関係するリソースを起点にする（ガイドの「overview に起点が無い事象」）。
- ユーザーが対象を名指ししていて overview にも出ていれば、確認を待たずに 5 に進む。そうでなければ、起点が合っているかと、足りない情報（時刻、Namespace など）を聞く。

## 5. 原因の深掘り
最初に `mg.sh report <case>` で報告書（`report.md`）を作る。ガイドの「原因の深掘り」と「コマンド」に従い、調査項目を上から調べ、1 段ずつさかのぼる。
- 調べた項目は `checklist.md` で `[x]` にし、結果（→ 事実 N、または → 未確認事項）を書く。次の段の「なぜ」が出たら、関係する確認事項の調査項目として足す。事象や確認事項は `checklist.md` だけを直し、`mg.sh report <case>` で報告書に写し直す。
- 確認事項 1 つ分の調査項目を調べ終えたら、`mg.sh items <case>` の出力と、分かったことを 1〜2 文でユーザーに示してから進む。
- 根拠にする行は、`mg.sh` の出力でファイルと行番号を確かめ、その都度、報告書の「確認した事実」に書き足す。
- ユーザーに聞いて「分からない」と言われた点や、must-gather に無い点は、聞き直さず、確かめるコマンドと一緒に報告書の「未確認事項」に書き足す。

## 6. 原因の確認
時系列の表（時刻・出来事・根拠）と「なぜ」の連なりで道筋を示し、原因（複数なら確度の順）と影響を添える。原因の見立てがユーザーの観測（直前の変更、時刻）と合っているかと、事象に気づいたきっかけ・ほかに困っていることを聞く。新しい情報は `checklist.md` の「事象」に書き、`mg.sh report <case>` で写し直す。合わない点や新しい情報があれば 5 に戻る。

## 7. 対処案
ガイドの「対処案と情報元」に従い、WebSearch / WebFetch（1 で MCP が使えれば、ナレッジベースはその MCP）で情報元を調べ、確認事項ごとの回答と対処案を整理する。見つかった情報元は 1 文ずつ伝えながら進める。情報元から、まだ調べていない原因や影響が分かったら、調査項目に足し、5 に戻って must-gather で確かめる。

## 8. 報告書
ガイドの「報告書」に従って、残りの節（概要、時系列、原因、対処案、情報元）を書き、書き足してきた節を見直す。`mg.sh lint <case>` を、`[NG]` と `[WARN]` が無くなるまで直す。lint で確かめられないことは、ガイドの「報告書」に従って見直す。

## 完了報告
報告書の概要（事象・原因・影響・推奨する対処）、確認事項ごとの回答、報告書と確認事項のファイルのパス、未確認事項（確かめるコマンド付き）、情報元の URL を伝える。

## ルール
- 調査はそれぞれ独立している。ほかのケースには触れず、案内もしない。
- クラスタに接続しない（`oc` を実行しない）。must-gather のファイルを変更しない。ツールのインストールは自分でせず、ユーザーに依頼する。
- ファイル全体やログ全体を読まない。`mg.sh` で必要な行だけを見る。
- 報告書や回答に、Secret の値、トークン、パスワードを書き写さない。
